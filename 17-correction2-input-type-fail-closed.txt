1. THE BLOCKER
================================================================================

C3 (Correction 1) compared a started workout's FROZEN input type against the
account's CURRENT one, read through useExerciseInputTypeLibrary().

That hook keeps `byExercise` deliberately EMPTY until status === 'ready'. So
while the read was in flight, and again after it had failed, every lookup
missed — and `modalityMismatchAt()` returned null.

Null meant "nothing to say", which the accordion read as "the modality is
settled and agrees". The consequence:

  - the calibration prompt rendered ("first set recorded at 20kg — how did
    that feel?")
  - Too light / Good / Too heavy were live
  - the stored suggested load was offered ("Use 20kg")

...before the current modality had been verified at all. An absent record was
being read as "weight", which is precisely the assumption Round 20 exists to
remove. That is FAIL-OPEN. On a slow or broken read it reproduces the original
Round 20 defect by assumption rather than by a stale setting.

================================================================================
2. THE RULE NOW IMPLEMENTED
================================================================================

For a STARTED workout exercise that has a frozen inputType, until the current
input-type library is successfully READY:

  - no actionable progression/calibration feedback
  - no suggested load
  - no inference that "no record" means weight
  - no manufactured mismatch

Once READY:

  A) current record exists and differs  -> existing mismatch warning,
                                           guidance paused, suggestion paused
  B) current record exists and agrees   -> normal accepted guidance
  C) no current record exists           -> genuinely unconfigured;
                                           no mismatch, normal semantics resume

If the read ERRORS: fail closed, with a truthful note —
  "Current input type could not be verified. Load guidance is paused."

Frozen workout controls are UNCHANGED in all cases. Failing closed withdraws
what the panel OFFERS; it never withdraws the controls the recorded sets are
written against. No UX redesign.

WHAT EACH CHANGE IS

inputTypeMismatch.ts
  modalityMismatchAt(sets, order, Map)  ->  modalityVerdictAt(sets, order,
                                            { status, byExercise })
  New ModalityVerdict:
      { kind: 'mismatch', frozen, current }
      { kind: 'unverified', reason: 'loading' | 'error' }
      null  (settled, nothing to say)
  THE GATE, before any map lookup:
      if (current.status !== 'ready') {
        return { kind: 'unverified', reason: current.status }
      }
  The status is taken structurally (CurrentInputTypes), so a caller cannot
  drop it without the compiler noticing — the old signature accepted the bare
  Map, which is exactly how the fail-open path was reachable.

ExerciseAccordion.tsx
  Prop mismatchAt -> modalityAt (AccordionMismatch -> AccordionModality).
  const verdict    = logging ? (modalityAt?.(index) ?? null) : null
  const mismatch   = verdict?.kind === 'mismatch'   ? verdict : null
  const unverified = verdict?.kind === 'unverified' ? verdict : null
  const actionable = verdict === null
  ExerciseGuidance renders only when `actionable`.
  suggestedLoad = actionable ? (lane?.suggestedLoad ?? null) : null
  New small note, [data-modality-unverified], carrying
  data-unverified-reason="loading" | "error". Rendered only where guidance
  exists to pause, so the Extra page — which never offers guidance — is not
  told something is paused that was never on offer.

TrainingSessionPage.tsx / ExtraWorkoutPage.tsx
  Both now destructure { status, byExercise } from the library hook and pass
  both halves to modalityVerdictAt.

exerciseInputTypeApiTestUtils.ts
  holdReads(): () => void — holds every GET open until released, mirroring the
  progression stand-in. This is how a test occupies the unverified window.

7.1  jsdom localStorage on Node 26

Under Node v26.5.0 the plain `npm test` reports 3 failures:

  progressionUi.test.tsx    > mirrors nothing into browser storage
  today.test.tsx            > never uses browser storage — the server is the only store
  todayPersistence.test.tsx > never uses browser storage

All three are the same TypeError: `window.localStorage` is undefined, with
Node emitting "localStorage is not available because --localstorage-file was
not provided". Node's own global shadows the jsdom one.

PROVEN PRE-EXISTING: the same 3 tests fail identically at the OLD SHA
(06368352) with the Correction 2 changes stashed. They are unrelated to this
work and were not "fixed" here — no repo config was changed for them.

The gate above was therefore run with

  NODE_OPTIONS=--localstorage-file=<scratch>/ls.db

which restores a real localStorage and turns all three green. Nothing else was
altered to make the suite pass.
